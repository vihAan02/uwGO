# UW GO — Architecture

Deterministic, typed, no LLMs. Business logic lives in `src/domain`, `src/parsers`, `src/rooms`, `src/engine`, `src/routing` and is independent of React. React components render `DayPlan` objects; they never compute recommendations.

```
Quest paste ──▶ questParser ──▶ ParsedSchedule (CourseMeeting[] + warnings)
WLU manual form ─────────────▶ CourseMeeting[]  (university: "WLU")
                                     │
                                     ▼
                      normalizeWeek(meetings, mondayISO)  ──▶ ScheduledClass[] per weekday
                                     │
                                     ▼
                     buildWeekPlan({ meetings, home, mondayISO, config }, provider)
                       │  per day, in this order:
                       ├─ 1. priceGapOptions  every way to spend each gap, + which we'd pick
                       ├─ 2. buildItinerary   the chain the student's answers imply (N stops → N+1 legs)
                       ├─ 3. resolve in order carrying the running location and clock
                       │       └─ resolveBestRoute ─▶ RouteMemo ─▶ RoutingProvider
                       └─ 4. emit DayPlanItem[] from the resolved chain
                                     ▼
                       WeekPlan ──▶ WeekView (timeline + map + Trip Mode)
```

## 1. Domain models (`src/domain/types.ts`)

```ts
type University = "UW" | "WLU";
type DayOfWeek = "M" | "T" | "W" | "Th" | "F" | "S" | "Su";     // Quest/UW-API day codes
type Component = "LEC" | "TUT" | "LAB" | "SEM" | "PRJ" | "PRA" | "DIS" | "TST" | "STU" | "FLD" | "CLN" | "OTHER";
type MinutesOfDay = number;                                     // 0..1439, local wall clock, America/Toronto

interface CourseMeeting {            // one meeting pattern (a Quest section can have several)
  id: string;                        // stable hash of the fields below (domain/ids.ts, djb2/base36)
  university: University;
  courseCode: string;                // "MATH 135"
  courseTitle?: string;
  classNumber?: number;              // Quest class nbr (4–8 digits)
  section?: string;                  // "001"
  component: Component;
  days: DayOfWeek[];
  start: MinutesOfDay; end: MinutesOfDay;
  startDate?: string; endDate?: string;   // ISO yyyy-mm-dd, this meeting row's own range
  location: RawLocation;             // { kind: "ROOM", buildingCode, roomNumber } | { kind: "ONLINE" } | { kind: "TBA" }
  instructors?: string[];
  unscheduled?: boolean;             // Quest showed no day/time (blank or TBA). Never routed.
  source: "QUEST" | "MANUAL";
  includeInPlan: boolean;            // false for TST by default and for anything the user hides
}

interface ParsedSchedule { term?: TermInfo; meetings: CourseMeeting[]; warnings: ParseWarning[];
  dateOrder: "DMY" | "MDY" | "YMD" | "UNKNOWN"; recognised: boolean }

interface CampusBuilding { id; university; code; name; aliases: string[]; latitude?; longitude?;
  coordinatesSource: "UW_ARCGIS" | "OSM" | "UNVERIFIED"; address?; kind: "ACADEMIC" | "RESIDENCE" | "MIXED" | "OTHER";
  parentCode?;                       // parent complex, e.g. SJ1 -> STJ
  floorRule: FloorRule;              // see §4
  residenceLabel? }                  // present => offered as a "where do you live" preset

interface CampusLocation { id; name; university?; latitude; longitude; kind: "BUILDING" | "HOME"; buildingCode? }
interface UserHome { name; latitude; longitude; address?; preset?: { university; buildingCode } }

interface ScheduledClass { id; day; date; start: Date; end: Date; meeting: CourseMeeting; location: CampusLocation; room: ParsedRoom }

interface RouteOption { mode: "WALK" | "TRANSIT"; durationMinutes; distanceMeters?; departureTime?: Date; arrivalTime?: Date;
  steps?: RouteStep[]; polyline?: string; transferCount?; provider: string; computedAt: string; isEstimate: boolean }
interface RouteStep { mode; durationMinutes; distanceMeters?; instruction?; transit?: TransitStepDetails }

interface ClassTransition { id; kind: "HOME_TO_CLASS" | "CLASS_TO_CLASS" | "CLASS_TO_HOME"; from; to;
  departAfter: Date; arriveBy: Date; hasDeadline: boolean; availableMinutes;
  walkingRoute?; transitRoute?; recommendedRoute?; recommendedDeparture?: Date; expectedArrival?: Date;
  feasibility: "COMFORTABLE" | "TIGHT" | "LIKELY_LATE" | "UNKNOWN"; reason?;
  consideredModes?: TravelMode[];    // what was actually priced, so "walking" reads as a choice
  crossCampus: boolean }

interface HomeReturnAnalysis { possible; recommendation: "WORTH_IT" | "POSSIBLE" | "NOT_RECOMMENDED";
  gapMinutes; travelHomeMinutes; usableHomeMinutes; travelBackMinutes;
  leaveForHomeAt?; arriveHomeAt?; leaveHomeAt?; nextClassStart; routeHome?; routeBack? }

type DayPlanItem =
  | { kind: "LEAVE"; at: Date; from: CampusLocation; transition }
  | { kind: "ARRIVE"; at: Date; to: CampusLocation; transition }
  | { kind: "CLASS"; scheduledClass }
  | { kind: "GAP"; from: Date; to: Date; minutes; homeReturn? }
  | { kind: "NOTE"; text: string };                    // e.g. a leg with no route

interface DayPlan { day; date; classes: ScheduledClass[]; transitions: ClassTransition[]; items: DayPlanItem[]; warnings: string[] }
interface WeekPlan { generatedAt; weekStartDate; days: Partial<Record<DayOfWeek, DayPlan>>;
  skipped: { meeting; reason }[]; usesEstimates: boolean }
```

Times inside `CourseMeeting` are minutes-of-day (no Date, no zone). They become `Date` instants only in `normalizeWeek`, via `TZDate` in `America/Toronto` for a concrete calendar date. This keeps parsing pure and makes DST correctness a single-module concern (`src/time/toronto.ts`).

Because `RouteOption` carries `Date`s, it cannot cross a JSON boundary directly. `src/routing/serialize.ts` (`serializeRoute` / `deserializeRoute`) is the only sanctioned conversion, and both the API handler and the localStorage cache go through it.

## 2. Parser architecture (`src/parsers`)

```ts
interface ScheduleParser { readonly id: "QUEST" | "LORIS"; readonly label: string; parse(text): ParsedSchedule }
```

`questParser` (`quest/QuestParser.ts`) is a **line-oriented island parser** (our own implementation, informed by the survey in DATA_SOURCES.md §2):

1. Normalize: split on `\r?\n`, then collapse every whitespace run inside a line to a single space and trim. Tabs and multi-space column separators therefore stop mattering; blank lines survive as empty strings and act as soft boundaries.
2. Reject wrong pages early with specific messages: Student Center homepage widget (its header row, or two of the surrounding page markers), "You are not registered for classes in this term", Course Selection page. The widget and course-selection checks are suppressed when a real `Class Nbr` table header is present.
3. Term header: `^(Spring|Fall|Winter) (\d{4}) | <level> | <institution>$`, falling back to any `Season YYYY` in the text. `termId` follows Quest's scheme, `(year - 1900) * 10 + {1 Winter, 5 Spring, 9 Fall}`.
4. Course header anchor: `^([A-Z]{2,10})\s+(\d{1,4}[A-Z]{0,2})\s+-\s+(.+)$`. Everything until the next course header is that course's block; inside a block, parsing starts after the `Class Nbr` header row when there is one, which skips the Status/Units/Grading furniture.
5. Then a state machine over the block's lines:
   - `^\(?(\d{4,8})\)?$` starts a new section row → the next two lines are section (`^\d{3}[A-Z]?$`) and component (`^[A-Z]{2,4}$`) when they have that shape. Some pastes put all three on one line ("1234 001 LEC"); that combined form is matched too.
   - A meeting pattern is: a days+time line (`^([A-Za-z]{1,12})\s+<time>\s*-\s*<time>$`, where the day token is expanded by `days.ts`) or `TBA` or a blank line; then a room line; then zero or more instructor lines; then a date range line `^<date> - <date>$`. An unrecognised day token yields a warning and the meeting is kept as `unscheduled` rather than dropped.
   - A meeting pattern that appears without a preceding class-number anchor is a **continuation row** of the current section (verified shape; the bug class other tools have).
6. Date order is inferred per document: try DMY, MDY, YMD; a candidate is accepted only if every date parses and every range is start ≤ end and lies within the term's plausible window (Fall: Aug–Dec, Winter: Jan–Apr, Spring: May–Aug). Ambiguous → `dateOrder: "UNKNOWN"`, dates dropped, warning shown; days/times still usable.
7. Room line → `RawLocation`: `ONLN`/`ONLINE` → ONLINE; `TBA` → TBA; `^([A-Z][A-Z0-9]*)\s+(\d+[A-Z]?)$` → ROOM (whitespace already collapsed, so `MC   4040` → `MC 4040`).
8. Output is fail-soft per course: an unparseable block yields a warning naming the course, never a silently wrong meeting. Duplicate meetings (same course, section, component, days, time, room, dates — i.e. the same stable id) are collapsed with a warning. `recognised` records whether the paste was a Quest List View at all, which is what the UI uses to tell "wrong page" from "no classes".

Quest is a UW system, so every meeting it produces is `university: "UW"`.

Fixtures: 7 real UWFlow pastes (MIT) in `test/fixtures/quest/` plus synthetic cases for edge conditions. Tests cover: normal lecture, LEC+TUT+LAB, multi-day, continuation rows, 5-digit class numbers, TBA room, TBA time, online, blank days line, tabs vs spaces, all three date orders, malformed paste, wrong-page pastes, duplicates, multi-instructor.

`laurierParser` (in `ScheduleParser.ts`) is a stub that returns a `PARSER_NOT_IMPLEMENTED` warning and points to manual entry. `src/parsers/manual.ts` validates the WLU manual form into a `CourseMeeting`, refusing buildings with no coordinates and `end <= start`.

## 3. Building registry (`src/data/buildings`)

`uw-buildings.generated.ts` is produced by `scripts/gen-uw-buildings.mjs` from a committed snapshot of the UW ArcGIS Buildings feature service (`scripts/uw-buildings-arcgis-2026-09-08.geojson`); it is machine-written and must not be hand-edited. `uw.ts` lays the curated overlay on top: residence and college labels, building kinds, aliases and floor rules. `wlu.ts` is hand-curated from Laurier's official pages, with OSM coordinates where noted.

`index.ts` exposes `findBuilding(university, code)` and `findBuildingAnywhere(code, hint)` with alias resolution (`E7`→`PSE` after the 2026 rename, `STP`→`UTD`, `DP`/`DANA PORTER`→`LIB`, plus each building's own aliases such as `BAB`→`BA` and `PETERS`→`P`), `residencePresets(university)` for the home picker, and `buildingLocation(b)`, which returns `undefined` for a building with no coordinates so uncoordinated buildings can still resolve by name without ever being routed. A Quest room code is resolved against the hinted university first; unknown codes stay unresolved and are reported, never guessed.

## 3b. Campus routing knowledge (`src/data/campus`)

The surveyed indoor network (§6, `indoorGraph.ts`) says where corridors run. It says nothing about whether a door may be used inwards, whether a link still exists, when a building is open or what is step-free. `src/data/campus` holds that, with how sure UW Go is of each fact and on whose word (see its README).

- `research/uwgo-routing-research-2026-09-14.json` is the research package as delivered: 49 buildings, 122 described door groups, 25 connections, 13 route candidates, 12 rules and 84 sources. It has no coordinates, hours or measured times, and routing is disabled on every record. `normalize.ts` reads it without adding anything and reports what it cannot map.
- `overlay.ts` is UW Go's reviewed decisions: which surveyed segment a research record is about (by canonical edge id, kind and buildings, held in agreement by a test), whether routing may use it, which way, its access and hours, plus the conflict register and the field-verification backlog. `node scripts/audit-campus-routing.mjs` renders all of it into `docs/campus-routing-audit.md`, which a test keeps current.
- Evidence is OFFICIAL, FIELD_VERIFIED (checked on the ground and deliberately promoted), CORROBORATED, SURVEYED (the WATIsGrass geometry: production today, silent on permission), ANECDOTAL, INFERRED or UNRESOLVED. Activation is ACTIVE, EXPERIMENTAL (only with `experimentalCampus`), QUARANTINED or HISTORICAL. A restriction is honoured whatever its evidence, because it only removes options; a claim that widens what a route may use needs official, field-verified or corroborated evidence; unresolved claims are never used.
- `field/` keeps field verification apart from routing. What someone records on the ground is a `FieldObservationFile` (a phone page that writes one is deferred; `field/README.md` says what a record holds); `node scripts/campus-field.mjs import` checks an export and adds it under `field/observations/`, which no routing code imports (a test holds this), and `review` shows what a target's observations support, what they disagree about, and a draft promotion. Only a reviewed promotion in `field/promotions.ts` changes a fact. Every claim in it must be something its observations saw (`field/rules.ts`, enforced by a test); a claim that confirms stronger evidence keeps that evidence, a changed value becomes FIELD_VERIFIED with the observations named on the fact, and a claim that would allow what stronger evidence restricts, or replace official hours, needs a stated `supersedes`. `npm run campus:field` ranks everything worth checking on the ground (§6, `fieldPriority.ts`) into `field/priorities.generated.json` and `docs/campus-field-verification.md`.
- In force: PAC's map point may be left but not entered, since its corner doors are exit-only, and the way into PAC is SLC's ground-floor link at the front desk, with SLC's east doors the corroborated entrance. The room-1501 DWE–RCH passage and the disputed TC–AL tunnel are quarantined. The old MC–DC, MC–M3 and DC–M3 bridges are historical and cannot come back through a survey import. SLC is open around the clock and TC weekdays 08:30–21:00. The EV1–HH tunnel and the E2–RCH link are never step-free, and the E3–E5 bridge is not independently accessible.

## 4. Room parser (`src/rooms/roomParser.ts`)

```ts
interface ParsedRoom { raw; buildingCode; buildingName?; roomNumber?; floor: number | "unknown";
  floorConfidence?: "verified" | "likely"; university?; resolved: boolean }
type FloorRule = { kind: "FIRST_DIGIT"; confidence; source }
              | { kind: "DASH_PREFIX"; ... }              // WLU DAWB "2-108"
              | { kind: "LEADING_DIGIT_THEN_WING"; ... }  // WLU Arts "1C16"
              | { kind: "UNKNOWN" }
```

`splitRoomString` handles spaced (`MC 2065`), glued (`BA201`) and WLU wing (`1C16`) forms; `inferFloor` computes the floor **only** from the building's rule, so a building without a verified rule returns `"unknown"` no matter how suggestive the room number looks. Every rule carries a cited `source`. UW `PSE` is `verified` from the E7 floor-plan PDF; UW `MC` is `FIRST_DIGIT/likely` from a single public data point and the UI labels it "unconfirmed".

## 5. Routing provider abstraction (`src/routing`)

```ts
interface RoutingProvider {
  readonly id: string;
  getWalkingRoute(from: LatLng, to: LatLng): Promise<RouteOption | undefined>;
  getTransitRoute(from: LatLng, to: LatLng, opts: { departureTime?: Date; arrivalTime?: Date }): Promise<RouteOption | undefined>;
}
```

- `GoogleRoutingProvider` (server only): REST `computeRoutes` with an explicit `X-Goog-FieldMask`, `travelMode: WALK` / `TRANSIT`, `departureTime` or `arrivalTime` for transit, and `transitPreferences.allowedTravelModes: [BUS, LIGHT_RAIL, RAIL]`. Only the two coordinate numbers are sent — callers pass richer `CampusLocation` objects and the Routes API rejects fields it does not know. Google's response types never leave this file.
- `CachedRoutingProvider` wraps any provider and takes a pluggable `RouteCacheStore`. Walking routes are keyed by rounded origin/destination coordinates (`pairKey`, 5 decimals ≈ 1 m) with a **30-day TTL** (Google Maps Platform Service Specific Terms §19.3); transit routes are keyed by (pair, departure-or-arrival minute) with a 10-minute TTL. It also de-duplicates in-flight requests for the same key, and **never caches a failure** — a route that did not come back is retried next time.
- `EstimateRoutingProvider`: straight-line distance × 1.3 detour factor at 1.35 m/s, minimum one minute. Used **only** when `GOOGLE_MAPS_SERVER_KEY` is absent, always returns `isEstimate: true`, and the plan screen shows a persistent "straight-line estimates" banner whenever `WeekPlan.usesEstimates` is set. Transit is never estimated; it returns `undefined`. This is a labeled fallback, not fake API output. `CachedRoutingProvider` never stores or serves an estimate, in either cache, so real routes replace them as soon as a key is configured.
- `HttpRoutingProvider` (browser): implements the same interface by calling `/api/routes`. The planner in the browser only ever sees `RoutingProvider`.

The two sides compose the same pieces differently:

| Side | Composition | Cache store |
|---|---|---|
| Server (`routing/server.ts`, `server-only`) | `CachedRoutingProvider(GoogleRoutingProvider ?? EstimateRoutingProvider)` | `MemoryRouteCacheStore`, process-wide; on serverless hosts that may be one request |
| Browser (`lib/routingClient.ts`) | `CachedRoutingProvider(HttpRoutingProvider)` | `LocalStorageRouteCacheStore` (`uwgo.routes.v1`, newest 400 entries, expiry per entry) |

Trip Mode is the one deliberate exception. `lib/tripRoute.ts` holds its own uncached `HttpRoutingProvider`, because a trip starting now needs a bus that has not left: a planned transit option is refetched live if it has already departed, was computed more than 3 minutes ago, or leaves more than 45 minutes out. Whatever comes back goes through the same `chooseRoute` the planner uses, with no deadline, so the trip only stays on the bus if the bus still wins from here; otherwise the student gets the walking route and a note saying why. Rerouting mid-trip is the opposite case and goes through the shared browser provider (`lib/routingClient.ts`, the same instance the week plan is built with), because the short walks that join a live position to a door of the indoor network repeat constantly and a cached one costs nothing.

## 6. Engines (`src/engine`, pure functions)

- `domain/laurier.ts` + `parsers/loris/`: **double degree**. A Laurier-hosted course already appears in Quest under a Waterloo subject with a `W` on the catalogue number, which both universities document (Laurier Enrolment Services; UW's Math Business pages and the BUS calendar entry). `classifyCourse` reads Quest's Campus column when the paste carries one and otherwise applies that convention, mapping the subject through a small table — `BUS`→`BU`, `ECON`→`EC`, `GESC`→`GESC` — and stripping only the trailing `W`, so `BUS 461AW` is `BU461A` and `GESC 231W` is `GESC 231` rather than an invented `GE231`. The subject must match as a whole token: Waterloo teaches its own `ECON`, and `ARBUS`, `AFM` and `BET` are Waterloo subjects. A `W`-suffixed subject with no known mapping is left as Waterloo and reported, never guessed. So a Quest paste alone creates every course a double-degree student has. `parsers/loris/` is enrichment only: `parseLorisSchedule` reads a LORIS (Banner) paste into records, and `mergeLaurier` attaches the professor and the Laurier room to courses that already exist, matching on Laurier identity then days and times, then section, then the course as a whole. It never creates a course, and it preserves meeting ids, because a meeting's id is a hash including its room and recomputing it would orphan the student's gap answers.
- `normalize.ts`: `CourseMeeting[]` → per-weekday `ScheduledClass[]` for the week starting at `mondayISO`, respecting each meeting's own date range, sorted by start. Meetings that cannot be placed (excluded, unscheduled, online, TBA, unknown building code, no coordinates, `end <= start`) go to `skipped` with a reason instead of being guessed at. Which week to show is a UI decision, made by `defaultWeekStart` in `lib/usePlan.ts`.
- `transitions.ts`: `buildItinerary(classes, home, gapStops, dateISO)` returns the day's `LegSpec[]` — a **chain**, not a set of independent hops. Each leg starts where the previous one ended. `gapStops` maps a class index to the ordered `GapStop[]` the student spends the following gap at, so a gap with N stops becomes N+1 legs instead of one: once the plan sends a student somewhere, the next trip sets off from there rather than from the classroom they have already left. A stop may owe a dwell (`minDwellMinutes`, the workout), which rides on the leg that *leaves* it as `dwellMinutes` and holds the planner's running clock — it cannot be derived later, because the itinerary is built before any route exists. Leg kinds name the shape (`CLASS_TO_STOP`, `STOP_TO_STOP`, `STOP_TO_CLASS`), and leg ids name what the leg joins rather than an ordinal, so a reminder keyed by leg id survives the student changing an earlier choice. `findContinuityBreaks` states the invariant as a check — leg *n* must start where leg *n−1* ended — and the planner turns any break into a visible warning. `buildTransitions` survives as a thin wrapper for the plain academic chain (empty `gapStops`).
- `bestRoute.ts`: `resolveBestRoute(request, fetcher, config)` prices the two outdoor answers to one trip — walking and transit — and picks between them. It is reached through `selectRoute.ts`, never called directly by a feature. It prices walking, decides via `shouldConsiderTransit` whether a transit itinerary is even worth asking for, and hands both to `chooseRoute`. A same-place request short-circuits to the zero-minute `SAME_PLACE` route with no call at all. Transit is asked the question the traveller actually has: with a deadline, the itinerary landing just before it (the latest useful departure), falling back to the first itinerary after the student is free if that bus would leave too early; without a deadline, simply the first one after they are free. `consideredModes` records what was priced, so "walking" can be reported as a choice rather than an omission. The walk it compares is the campus-aware one from `campusRoute.ts`; whether transit is worth asking for is still judged on Google's own walk, so campus knowledge never changes which itineraries are requested.
- `selectRoute.ts`: the **one** place a trip becomes a route. `selectRoute(request, deps, config)` takes two places, a departure window and the student's route preference, and returns the outdoor walk, the bus or the winter route — whichever the app's own rules pick. Every leg of the week comes through it, and so does every reroute in Trip Mode, so a route recomputed from where a student is standing is chosen by exactly the rules that chose the one they set off on. `resolveBestRoute` answers walking against transit; the winter route from `indoorRoute.ts` then displaces the walk only when the student asked for indoors, the fastest answer was on foot in the first place (a chosen bus is never overridden — that decision was about time) and `indoorIsReasonable` says staying inside does not cost unreasonably more. The plan always prices the winter route, because the timeline offers it as an alternative row; a live reroute passes `indoorAlternative: false` under FASTEST, because an option that cannot be recommended is not worth the door lookups it costs. `livePosition(latLng)` wraps a GPS fix as an origin, which is how a reroute gets `live position → outdoor connector → indoor network → destination` out of the same machinery, with `MIN_INDOOR_SHARE` and `indoorIsReasonable` keeping it from forcing a tunnel on someone standing across the way from their destination.
- `departure.ts`: `recommendedDeparture = arriveBy − ceil(duration) − arrivalBuffer`, plus `clampDeparture` so a plan never tells a student to leave before the previous class ends. Minute-exact integer arithmetic on `TZDate`.
- `feasibility.ts`: `assessFeasibility` judges a duration against the time available — `COMFORTABLE` if `available ≥ ceil(travel) + arrivalBuffer + comfortMargin`, `TIGHT` if `available ≥ travel`, else `LIKELY_LATE`. `assessResolvedFeasibility` judges a *resolved* leg, and treats transit differently on purpose: an itinerary asked for by arrival lands near the buffer by design, and the minutes spent waiting at the origin are free time, not travel. So transit is scored on where it lands — late if it arrives after `arriveBy`, `TIGHT` if inside the buffer — rather than on a wait it did not cost the student.
- `gapOptions.ts`: `priceGapOptions` prices every way to spend one gap — stay, rez, the nearest library, and the gym followed by rez, a library or straight to class — through the injected `resolve`, on the same clock `buildItinerary` will carry, so an option the student picks costs no extra call and the card's numbers are the timeline's numbers. Usable time is measured from arriving (or the doors opening) to having to set off, and after a workout from the **end** of the workout; never from raw gap length. The single exception is an arithmetic pre-filter for gaps too short to hold the workout and the buffer alone, which can only produce true negatives. An option whose route could not be fetched is withheld rather than given an invented duration; one that is merely tight is offered and marked. `recommendGapOption` then walks `GAP_LADDER` — gym+rez, gym+library, gym+class, rez, library, stay — and stars the first rung that qualifies. It is pure and synchronous, and needs no knowledge of whether the student works out: with the gym off, those options are simply absent.
- `indoorGraph.ts` / `indoorRoute.ts`: the **winter route**. `src/data/indoor/` holds a graph of the campus tunnels, bridges, hallways, doors, stairs and the short outdoor walkways between them (generated from the WATIsGrass survey; see the README there for provenance and licence). `indoorGraph.ts` runs Dijkstra over it from every entry point of the origin building to any of the destination's, with an edge's cost being its seconds and seconds outdoors counted `OUTDOOR_PENALTY` (4) times over, so the route stays under cover unless the indoor way round is far longer than the dash outside it saves. `indoorRoute.ts` joins the student's actual places to the graph — inside a network building by the short walk from the registry's point to the entry point; from anywhere else (a residence) by a Google walk to the nearest door, priced through the plan's route memo, never a straight line — and returns the same `RouteOption` every other route is, with the whole journey's polyline, `indoorPath` (the buildings passed through) and `indoorShare`. It gives nothing rather than a mostly-outdoor route or an invented link, so the "Winter route" row simply does not appear where the network has nothing to offer. The search runs over directed arcs built from the campus knowledge (§3b): a door documented as exit-only is not an arc inwards, a quarantined or demolished link is not an arc at all, a closed segment is removed, and, when a time is given, a building a route only passes through is used only while it is open (with its hours unknown, 07:00–22:00, which is UW Go's policy rather than a fact about the building); a trip that starts or ends in a building is never refused by that building's hours. Changes of floor keep the survey's kind (`STAIRS`, `ELEVATOR`, `RAMP`, `OTHER_VERTICAL`) and are timed by it; step-free needs refuse stairs, and refuse an elevator or ramp until it is documented as step-free, so an elevator is never assumed accessible. The survey records no elevators at all, so step-free routes do not change floor until one is confirmed. Ties break on node id, so the same question always gives the same route.
- `campusRoute.ts`: the **campus-aware fastest walk**. Google walks between campus-map points, and cannot know that PAC's corner doors are exit-only or that cutting through a building beats walking round it. `campusWalk` builds the alternatives over the constrained network with a fastest-walk cost (outdoor walkways timed at indoor pace, since the survey draws them straighter than the paths are; nothing extra for official or corroborated crossings, 10 s for surveyed ones, more for experimental ones) and compares them with Google's walk. When Google's walk relies on a way in that may not be used, or runs along a closed path, the best allowed route is taken whatever it costs (`CORRECTED`). Otherwise a campus route is taken only when it saves `campusShortcutMinBenefitSeconds` (60: Google's time is kept to the second, but the indoor part is estimated and the timeline shows minutes) and either passes through a building or uses a different door with Google timing the whole walk outside (`SHORTCUT`, `BETTER_ENTRANCE`). If nothing allowed can be routed, Google's walk stays with a warning (`NO_USABLE_ROUTE`). Google is asked only for the door walks the winter route already prices and, when Google's own walk cannot be used, up to three walks to allowed entrances, and never unless a straight-line lower bound says the answer could matter. It runs inside `resolveBestRoute`, so the itinerary, the gap options, the gym windows and Trip Mode all walk the same way. Every decision (`CampusDecision`, kept on the leg) names what it chose, what it rejected and why; `explainCampusDecision` prints it, and `campusDebug.ts` exports the whole graph with its rules as GeoJSON. `PlanInput.campus: false` plans Google's walks exactly as they come. A `CampusLocation` may carry a floor, which starts or ends the network search there; schedules do not set it yet, because the plan's route cache promises one answer per building pair. Every decision also records what activated it (a building's rule, students' closure reports, or the doors and links of a shortcut) and what each door and link it uses rests on, as `CampusProvenance` from `campusProvenance.ts`: official research, community reports, UW Go's review, the WATIsGrass survey, a promoted field observation with its date and verifier, or a combination. The reasoning prints it, and in development `window.uwgoCampus.legs()` lists it for every planned leg and `window.uwgoCampus.provenance(edgeId)` for any segment.
- `fieldTargets.ts` / `fieldPriority.ts` / `fieldVerificationDoc.ts`: **what to check on campus, in order**. `buildFieldTargets` makes one target per surveyed door to outside, link between buildings and change of floor, per research door group not matched to a surveyed door, per building rule, per network building's hours, per reviewer check no single place answers, and per research lead that is not routed; each says where to stand (a surveyed position, or only the building's map point when there is none), what UW Go believes and on whose word, why it needs checking and exactly what to check. `analyseFieldPriorities` ranks them from what UW Go actually routes: the campus-aware walk decision for every pair of network buildings and residences against a stand-in for Google's walk (so no API is asked), and winter and step-free routes between every pair of network buildings, each trip weighted by its two places (size from surveyed corridor length, times the roles UW Go's data gives a building: the gym, SLC, a library, a residence, floor-plan classrooms). For each target it measures reliance, the cost of losing it (every relying trip decided or routed again with it closed) and the value of confirming it (a quarantined link usable, a step-free elevator at a stairwell), with separate uncertainty for using it and for its access. P0 is anything unverified that is critical (PAC's rule, the only allowed way into PAC) or that UW Go sends students through instead of Google's walk while a reviewer has flagged it; anything else UW Go sends students through is at least P1. `npm run campus:field` writes the ranking with a fingerprint of its inputs, and a test fails when the fingerprint or the rendered document is stale.
- `networkRegression.ts`: **route regression**. Every ordered pair of network buildings routed as the fastest walk's network search, the winter route and a step-free route, compared route by route between two versions of the network or the knowledge. `scripts/gen-indoor-network.mjs` compares its output with the committed network (`data/indoor/networkDiff.ts`) and will not replace a changed one without `--accept`; `--out` writes a trial copy, and `npm run campus:regression` with `UWGO_NETWORK_CANDIDATE`, `UWGO_ROUTES_OUT` or `UWGO_ROUTES_BEFORE` lists every route a regeneration or a promotion changes.
- `homeReturn.ts`: takes two `ResolvedLeg`s (a route plus the door times it was resolved for) rather than raw durations, so the answer accounts for the real thing — a bus that only runs at :05 and :35 costs exactly what it costs. `usable` is read straight off the legs as arrive-home → leave-home. `possible` also requires the return leg to land before the buffer. `WORTH_IT` at `≥ minUsefulHomeMinutes`, `POSSIBLE` at `≥ minPossibleHomeMinutes`, else `NOT_RECOMMENDED`.
- `transitCompare.ts`: `shouldConsiderTransit` = cross-university, or a walk at least `transitConsiderWalkMinutes` long, or no walking route at all to compare against. `chooseRoute` then treats walking and transit as two answers to one door-to-door problem, transit priced as the complete itinerary (walk to the stop, ride, transfers, walk from the stop). Whichever arrives on time wins; when both do and there is a deadline, transit must clear `minTransitSavingMinutes` on **net** time — travel saved, minus any time it forces the student to set off earlier, minus `transitTransferPenaltyMinutes` per transfer. Catching a bus 30 minutes early to save 6 minutes of travel is a loss. Without a deadline (going home) the question is simply who arrives first, wait included. Ties and anything under the margin go to walking: no wait, no bus to miss. Every outcome carries a `reason` naming the numbers, including the case where transit was asked for and nothing came back — which must not read as "not looked".
- `closures.ts` / `closureGeometry.ts`: **crowdsourced closures**. `closures.ts` turns the database's anonymous tallies into the set of segments routing must avoid: five distinct accounts, within a 24-hour window, counted once per account. The window is a product decision recorded there and in the migration — campus closures are mostly same-day facts, and a closure that really lasts is kept alive by people continuing to meet it and report it, each report refreshing that account's row rather than adding another. Segments are identified by the canonical id in `data/indoor/edgeId.ts`, derived from a segment's kind and endpoints rather than its position in the generated array, so regenerating the network cannot silently re-point stored reports. `routeBetweenNodes` removes closed segments from the search outright, so a shut tunnel costs a detour and never the journey; `indoorRoute.ts` runs the search a second time without the closures only when there are any, purely to name what the route went round. `closureGeometry.ts` covers the case our own graph cannot: a Google walking route has no edges and the Routes API cannot be told to avoid a footpath, so a fastest route is checked against closed outdoor segments geometrically, marked with `blockedBy` when it runs along one, and `selectRoute` then prefers an indoor way round. Doors to outside, links between buildings and the corridors of a building a route passes through can be reported too, and a campus-aware walk is built with closed segments removed and treats a Google walk along a closed path as unusable.
- `planner.ts`: the async orchestrator, and the only module that touches a `RoutingProvider`. Each day runs in four steps: **price the gaps** with the best route each way and star one option, **build the itinerary the student's answers imply** — an unanswered gap builds nothing, and picking the gym without answering "and then where?" builds nothing either, **resolve the legs in order** carrying a running location and clock so a leg can never set off before the previous one has landed, then **emit the timeline** from that same resolved chain. A per-plan `RouteMemo` fetches each walking pair once for the whole week and traps provider errors; a `LegResolver` memoizes by (origin, destination, window), which is what makes the routes a go-home decision was made on the very routes the timeline goes on to show. Any leg left without a route becomes a `NOTE` item plus a warning, never a fabricated duration, and a failed provider call leaves `feasibility: "UNKNOWN"`.

`PlannerConfig` defaults (`src/domain/config.ts`): `arrivalBufferMinutes: 10`, `minUsefulHomeMinutes: 30`, `minPossibleHomeMinutes: 10`, `comfortMarginMinutes: 5`, `transitConsiderWalkMinutes: 10`, `minTransitSavingMinutes: 5`, `transitTransferPenaltyMinutes: 3`, `buildingExitMinutes: 0`, `minGapForHomeAnalysisMinutes: 20`, `campusShortcutMinBenefitSeconds: 60`. Every number there is a product decision, not a constant of nature. `USER_CONFIG_KEYS` marks the ones the student actually chooses — currently just `arrivalBufferMinutes` — and only those survive a reload; see §8.

## 7. Time handling (`src/time/toronto.ts`)

All wall-clock construction goes through `torontoDate(dateISO, minutesOfDay): TZDate`; arithmetic and formatting go through `addMin`, `minutesBetween`, `formatClock`, `formatDuration`, `mondayOfWeek`, `dateForDay`, `weekdayOf`. Formatting uses `date-fns` with `@date-fns/tz` pinned to `America/Toronto`, so neither the developer's nor the user's machine zone is ever consulted. Tests pin the second Sunday in March and the first Sunday in November. No code path uses `new Date(y, m, d, h)`.

## 8. Frontend structure (`src/app`, `src/components`)

- `/` — the landing page (`src/app/(landing)`, a route group so its components, styles and design notes stay together). Public; its Get Started buttons go to `/login`. A signed-in user who opens `/` is redirected to `/plan` by the proxy (`decideAuth` → `TO_APP`). The old preview path `/landing` is a permanent redirect to `/` in `next.config.ts`.
- `/login` — email sign-in. On success it replaces itself with `/plan`, so back never returns to the form.
- `/setup` — `Onboarding`: paste box, parse preview with warnings, WLU manual add, home picker, buffer picker, "Build my routes". Redirects to `/plan` once a schedule is stored, and "Build my routes" replaces the history entry so back from the plan does not bounce through setup.
- `/plan` — `WeekView`: week navigation (previous/next/Today), weekday tabs, the next-class card, the day timeline, and one map, with a settings sheet over the top. Redirects to `/setup` when there is no schedule.
- `NextClassCard` leads with what matters now — course, room, floor, travel time and the exact minute to leave, counting down live — using `lib/nextClass.ts` (`findNextUp`), which prefers a class in progress, then the next unfinished class in the week, and falls back to a labelled preview when a past or future week is being browsed.
- `DayTimeline` renders `DayPlanItem`s only; it computes nothing. Tapping a class or a leg calls back into `WeekView` to retarget the map. When campus knowledge changed a leg, the leg says why in one line (for PAC, that its corner doors are exit-only and which door the route uses instead); the full reasoning is never rendered, only reachable from the console in development (`window.uwgoCampus.legs()`).
- **One map instance.** `MapPanel` (`@vis.gl/react-google-maps`, lazily imported, `ssr: false`) takes a `MapSelection` — a `LEG`, a `PLACE`, or the whole `DAY` — and re-frames itself. A second CSS-hidden copy would double Dynamic Maps billing and compute its zoom from a zero-size box, so the map is placed by grid position rather than duplicated. Without a route polyline it draws a dashed geodesic line.
- `TripMode` is a separate fullscreen map for a trip starting now: a flat 2D map (the tilted camera stuttered on phones), the live position, and the freshness logic from `lib/tripRoute.ts`. Position and heading are separate sensors and are never guessed from each other: `watchPosition` gives where the student is, `lib/useDeviceHeading.ts` gives which way the phone faces from the orientation sensor (Safari's `webkitCompassHeading`, or an absolute `alpha`; iOS permission is asked for by a tap in the trip), and with no trustworthy heading the marker is a plain dot on a north-up map. Both feed refs, not state: one animation loop in `TripCamera` moves the marker, turns the viewfinder cone and eases the camera (`lib/tripCamera.ts`, heading-up when the compass is on and the map is vector, otherwise re-centring only once the student leaves the middle of the screen); a pan, pinch or wheel stops following until Recenter. Remaining time and distance come from `lib/routeProgress.ts`: each fix is projected onto the chosen route's own polyline and Google's distance and duration are scaled by what is still ahead (on transit the time left is simply time to Google's arrival). Leaving the route is judged on every fix and answered rarely: `lib/tripReroute.ts` (`TripRerouter`) asks for a new route only once three consecutive usable fixes agree the student is more than 60 m off it and at least 20 s have passed, never twice inside a minute, and never while a request is already in flight. 60 m is chosen for walking on campus, where a phone between buildings is routinely 15-30 m out and the paths either side of a green run 20-40 m apart. The replacement comes from `rerouteFrom`, which calls the same `selectRoute` the plan uses with the trip's own destination and route preference, so an outdoor trip can become a winter one and a winter one can go back outside, whichever is now the better way from where the student actually is; the header's mode word and the note say which. A reroute that fails, or that could only be answered with a straight-line estimate, returns nothing and the route already on screen stays. Transit is never rerouted: a bus off its usual road is still the bus.
- `lib/mapsLinks.ts` builds keyless Google Maps URLs (`/maps/dir/?api=1`) so every leg is openable in the Google Maps app even with no keys configured; only coordinates go into those URLs.
- `GapChoicePicker` is the one place a student changes the plan's shape. It renders `GAP.options` — labels, numbers, the star, and whether an option fits are all decided by the engine — and reports back through `store.setGapChoice`. Its only state is an optimistic echo of the student's own tap, adjusted during render rather than in an effect, because choosing rebuilds the whole week asynchronously and the button would otherwise sit unlit until the routes came back. An option that does not fit is rendered disabled with its reason rather than hidden. The segmented control is shadcn/ui's Toggle Group (`src/components/ui/toggle-group.tsx`), also used by the buffer, home, route and gym pickers.
- `DayTimeline` shows the *real* margin on an arrival — the minutes between the expected arrival and the class start — not the configured buffer, because a tight hop can land later than intended and the student should see that.
- Gap answers live in `AppState.gapChoices` as two maps: `byDate` (`${dateISO}|${classId}`) for "this Thursday" and `byClass` (`${classId}`, stable across weeks because `ScheduledClass.id` is `${meetingId}:${day}`) for "every Thursday". The day's answer wins. There is deliberately no `everyWeek` flag on a choice — presence in `byClass` *is* the flag, so a derived answer can never disagree with the maps it describes. `src/lib/gapChoices.ts` prunes day answers older than the Monday of the current week (not older than today, or looking back at Monday on a Friday would blank a card the student remembers filling in), caps the store the way `routeCacheStore` does, and forgets a class the student drops. Per device, and never saved to the account: it is a decision about one afternoon, not a preference.
- State: a React context store (`src/lib/store.tsx`) over a versioned localStorage envelope (`src/lib/storage.ts`, `AppState`, key `uwgo.state.v1`, `migrate()` on read). `loadState` runs after mount only, never during SSR, and every read and write swallows quota/private-mode failures so the app keeps working from memory. `migrate` restores only the keys in `USER_CONFIG_KEYS`; every engine threshold comes from the current `DEFAULT_PLANNER_CONFIG` on each load, so retuning the engine takes effect immediately instead of leaving returning students on numbers saved months ago.
- Account copy: a signed-in student's schedule and preferences are also saved to Supabase, one `public.user_state` row per account with Row Level Security (`supabase/migrations/20260911000000_user_state.sql`). `src/lib/userState.ts` maps app state to the row and validates everything read back field by field, dropping what does not fit. `src/lib/userStateSync.ts` reads the row on sign-in and decides whether to take the account's copy, upload the device's (newer unsaved changes, or a schedule the account lacks), or leave both alone; it never writes before a successful read, discards a device copy tagged with another account, saves preference changes after a pause and saves at once when onboarding finishes or the schedule is replaced. `UserStateProvider` connects it to the store and gives `/plan` and `/setup` a loading state, so onboarding never flashes before a saved schedule arrives, and an error state that keeps the device's copy.
- `/courses` — `CoursesView`: the student's academic profile and weekly timetable, built from the same `user_state` schedule the plan uses; there is no second schedule store. Courses are grouped from meeting rows by `lib/courses.ts`, titles come from the student's own import and fall back to a small reference set in `data/courses/metadata.ts` only where the import had none, and Laurier courses carry their Laurier code and are marked when Quest gave no room or professor. The timetable is adapted from UW Flow's calendar (MIT; files listed in `THIRD_PARTY_NOTICES.md`) and split three ways. `lib/timetable.ts` is the geometry: one `HOUR_HEIGHT`, and `timeToY` / `durationToHeight` as the only conversion from time to pixels, used by the grid lines, the hour labels and the blocks alike; the lane packing that closes an overlap group only when every lane in it has ended; the hour range (9 to 5, widened to whole hours over the whole term so the grid never jumps between weeks); and `blockLines`, which decides from a block's height which lines it shows (code, time, section, room) using the same padding and line heights the markup renders with, so text is dropped rather than left to escape a short block. `lib/calendar.ts` is the dates, all Toronto ISO dates: a meeting occurs on a date only on its weekdays and within its first and last dates (`domain/meetingDates.ts`, the same rule `engine/normalize.ts` uses for the plan), the week opens on today or on the first day of classes before term, steps by day, week or month, and is titled "Sep 21st – 25th, 2026" with a weekend column only when a class falls on it. `lib/courseColors.ts` is a fixed eight-colour palette whose contrast is checked by test, assigned alphabetically until the student picks one; choices are keyed by canonical course code and saved as `preferences.courseColors` in `user_state`, so they follow the student across devices and survive a schedule update. `components/courses/Timetable.tsx` only draws: week view by default, day view by default under 768px (a phone scrolls the week sideways at a readable column width rather than squeezing it), and a month view whose days open the day or week. Nothing on this page depends on a live UW Flow request.
- Closure reports: `public.route_closure_reports` (`supabase/migrations/20260912000000_route_closure_reports.sql`) holds one row per account per segment, timed by the database so a report cannot be backdated. Row Level Security limits every row query to the student's own reports, so nobody can read who reported what; the shared picture comes from `route_closure_consensus`, a view that exposes only a segment id, a count and a timestamp. `lib/ClosuresProvider.tsx` reads it and hands the confirmed set to the planner and to Trip Mode. With no account, no Supabase, or a failed read the set is empty and every route is computed exactly as it was before.
- PWA: `public/manifest.webmanifest` + a minimal service worker that only makes the app installable — it caches no routes, because routing data must stay fresh.

## 9. API boundary (`src/app/api`)

| Route | Method | Input | Output | Notes |
|---|---|---|---|---|
| `/api/routes` | POST | `{ mode: "WALK" \| "TRANSIT", from: LatLng, to: LatLng, departureTime?: ISO, arrivalTime?: ISO }` | `{ route: RouteOptionJSON \| null, error?: string }` | Validates the coordinates are finite and inside the Waterloo Region bounding box; uses the server provider; sets `X-UWGO-Routing: google \| estimate`; never logs bodies. |
| `/api/routes` | GET | — | `{ mode: "google" \| "estimate" }` | Lets the client tell whether real routing is configured. |
| `/api/geocode` | POST | `{ address }` | `{ result?: { latitude, longitude, formattedAddress }, error? }` | Google Geocoding, `region: ca`, bounded to Waterloo Region. 503 when no server key. A vague or partial match outside the region is reported as "not found" rather than "outside the region". Not stored server-side. |

Both handlers run on the `nodejs` runtime. Keys: `GOOGLE_MAPS_SERVER_KEY` (server only; API-restricted to Routes API + Geocoding API), `NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY` (HTTP-referrer restricted; API-restricted to Maps JavaScript API), optional `NEXT_PUBLIC_GOOGLE_MAPS_MAP_ID`. `.env.example` explains which prefix means public and which means secret; the README documents the Cloud Console restrictions. A raw browser `fetch` to Routes cannot be referrer-protected, which is why routing goes through the server.

## 10. Privacy and cost rules baked into code

- No analytics, no error telemetry with request bodies.
- The client sends coordinates and times, never course data, to `/api/routes`.
- Walking routes cached per building pair ≤30 days; transit cached ≤10 minutes; failures never cached.
- One map instance on the screen at a time, re-framed rather than re-created, so changing the selection does not bill another map load.
- The planner memoizes walking pairs across the whole week, so a 15-transition week costs at most the number of distinct building pairs.
